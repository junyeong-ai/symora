# JSON Output Is the Public API

These files emit or shape the JSON that downstream agents parse. Treat any field rename, removal, or structure change as a breaking API change.

## Stable field names for list-style responses

- `count` — total matches found
- `showing` — number actually emitted in `items`
- `items` — the result array
- `truncated` — boolean indicating `showing < count`, whether from an item cap (`--limit`, config limits) or from the per-response size ceiling (`output.max_response_chars`, applied once in the output layer as the last step before emission).
  - A size-driven reduction always appends a hint naming the config key.
  - Items are only ever dropped whole — per-item shape never changes with response size.
  - Layering: at most one budget governs a response. A command-level content budget is token-denominated and applies inside the command (e.g. `pack --tokens`); a response that states one (`budget_tokens`) is what the caller asked for and the transport ceiling does not re-cut it, so its `estimated_tokens` keeps describing what was emitted. Every other response is bounded by `output.max_response_chars`, measured on the compact serialization in every format — the ceiling bounds the answer, not its typography, so `--format` never decides which items a caller receives. Don't add a third budget vocabulary.
- `map`'s enumerated lists are list-shaped rather than bare arrays — `entrypoints` and `top_directories` on `summary`, `child_directories` and `files` on `dir`, `siblings` on `file` — because each is a set a limit cuts and no neighbouring total covers it: `summary`'s `directories` counts every directory holding code, not the top-level areas listed beside it, and `dir`'s `file_count` counts the whole subtree, not the immediate files. A ranking over a pool with no meaningful size stays a bare array (`related_files`).
- `backend` — what produced an answer, over the producers that surface has. On `search` rows: `index`, `workspace`, `document`, `scan`. On a file-scoped symbol answer (`symbols <file>`, `map file`): `document` — the language server's tree, nested, carrying its own kinds — or `ast`, the compiled-in grammar read from the file's bytes, which is flat and carries containment in `name_path` alone. A symbol-path answer (`symbols --symbol` / `--name`) merges the index with a live lookup, so it carries `index` or `workspace` per ROW rather than one word for the response. Always present where an answer has more than one producer, because what a caller may read into absent nesting depends on it. `map file` omits it with `focus_symbols` when neither producer read the file.
- `stale` — present (true) only when index-served rows came from files that changed on disk after indexing; re-run `symora search index build` to refresh
- `score` — a row's relevance as the share of an exact match it earned, and the value the answer was ordered by, so it never climbs as the answer descends and a threshold keeps the rows a reader meant to keep. A symbol answer ranks on more than the text — the kind, whether the file is test material — so the index's own match tier is not it.
- `test_caller_ratio` (`impact`'s `blast_radius`) — what share of the CALLERS in the graph are test code. Absent when there are none, because a share of nothing is not zero. Distinct from `impact`'s `coverage`, which counts the test REFERENCES to the symbol: a type is referenced and never called, so the two answer different questions and a symbol may hold one and not the other.
- `confidence` (`impact`'s `blast_radius`) — reaches 1.0 only when the caller walk both found direct callers and exhausted the graph. 0.8 means it stopped at its own depth or fan-out bound; 0.5 means there were no direct callers to walk, a state a true leaf and an unsupported capability share, so neither earns more. How DEEP the graph turned out to be earns nothing on its own: a shallow walk that ran out is complete, a deep one that hit the cap is not. A dynamically-dispatched anchor is capped at 0.7 whatever the walk found, because its graph is a known lower bound.
- `test_files` (`usage --metrics`) — every distinct file whose test material references the symbol, so how many are listed is how many there are; omitted when there are none, and when `--metrics` was not asked for. A sample here would be compared across rows as a count.
- `declared_symbols` (`pack`'s file rows) — how many signatures the file states, present only when `--per-file` showed fewer, so a shape and a whole one read apart. The cap is the request's, never the cache's: a cached list already cut to one request would answer the next in its shape.
- `is_exported` — present only for a language whose visibility the compiler decides (Rust, Go, Java, Kotlin, C#, TypeScript, JavaScript). Absent elsewhere, because a naming convention is not a visibility rule and a language this reads nothing for would otherwise publish "not exported" as a fact about the reader. `impact`'s `risk` escalates on it, so an absent value escalates nothing rather than escalating on a guess.
- `hints` — optional next-step suggestions for the agent; also emitted as a top-level field by `impact` and `context`, whose reference counts are otherwise published without anything to qualify them.
  - A zero reference count on a MEMBER carries one: a call reaches a member through the type that declares it — construction, dispatch, a protocol satisfied structurally — and none of those name the member, so the zero is not reachability. The hint names the declaring type and how often it is used, because that is what separates the two readings: a used type leaves the member reachable, an unused one makes the zero the stronger claim. A free item has no such route and its zero stands bare. `impact` needs this most, since it publishes a `risk` verdict derived from the count.
- `next_commands` — optional ready-to-run follow-up commands (omitted when empty); also emitted as a top-level field by non-list outputs (`map` summary, `impact`)
- `bodies_included` — present only on sections where body attachment ran (`context --with-bodies`) and that still contain items: always equals the number of `items` carrying a complete `body`.
  - Items without `body` under it were omitted — token budget exhausted, symbol unresolvable at the item's position, or genuinely bodiless (prototypes, interface methods) — disclosed, never silent.
  - If the transport size ceiling drops items from the section, the fitter recounts this field against the remaining items (removing it when the section empties), so the equality holds in every emitted response.
- `indexing` — degradation marker, present only when the answer was computed under degraded workspace *language-server* indexing (e.g. `"timed_out"`). Carried by every answer whose completeness depends on that indexing, list-shaped or not: `def`, `typedef`, `hover` and `signature` are one answer rather than a set, and there the marker is what separates "the server settled this and there is nothing here" from "the server was still reading the workspace" — the same JSON otherwise. `rename` carries it on a preview and refuses to apply under it, since an edit set computed from a lower bound rewrites some call sites and leaves the rest. Not a home for "the symora index took no part in this answer": the two prescriptions are opposites — `indexing` says the server's answer is a lower bound that retrying can raise, while an index that is rebuilding contributed nothing and the answer came from somewhere else entirely. Folding them into one field would leave an agent unable to tell "wait for the server" from "wait for the index"; the rebuild says so in `hints`/`next_commands`, and its machine-readable form is `is_indexing` on `search index status`.
- `coverage_gaps` — array of `{language, reason}` pairs naming languages a search did not cover, so a short or empty result is never mistaken for "nothing exists"; omitted when empty. Emitted by symbol `search` (a `Section` field) for every requested language the answer could not vouch for — one outside the index's build scope whose live lookup also failed, was never made, or was cut short — regardless of how many results came back, since a partial answer hides a missing language better than an empty one; and by `usage` (its own top-level field) when some languages failed or were skipped. What the index covers is a property of the build, never of the query: a language the build scoped to is in the answer's domain whether it matched or not, so a legitimate zero over it is never a gap. Stable `reason` codes: `not_indexed`, `server_not_installed`, `not_consulted`, `timed_out`, `unsupported`, `unavailable`, `not_searched`.
- `incomplete` — present (true) only when `count` is a lower bound rather than everything the answer's own sources held; omitted whenever the answer holds all of it. One meaning, several causes. Where the response carries `hints`, the cause leads them, because the remedies differ; the surfaces without a `hints` field carry `unread_paths` beside the flag instead (`map summary`, `map file`, `map dir`, `pack`) or, where the cause is the language server's own reference set rather than the tree, the flag alone (`refs`' sibling `incomplete` on `impact`/`context`). The meaning is the same:
  - `refs` (and `refs.incomplete` on `impact`/`context`): the language server's reference set omits the very usage the query was made from.
  - every `search` surface that counts matches (`symbols`, `content`, `ast`, `semantic`): paths the walk could not enter, open, or finish reading; an index built while some paths could not be read (see `unread_paths`), which leaves it short for the languages those paths could hold; a path-like symbol query whose widening into document symbols was cut short — or never attempted, because the page had already filled, which leaves the same files unopened and takes the same raised `--limit` to reach; an index page that filled before the index ran out of rows; or, on a path-like symbol query, live and indexed results that overlap while at least one source was not materialised whole, so their union can be bounded from below but not counted — deduplication settles the overlap only while both sets are in hand.
    - A documented, configurable exclusion is not a hole: a binary file, or one over `search.max_file_size_mb`, is outside the search's domain the way `--limit` is outside its emission. Only failures set this — and only failures that leave the content unknown. `NotFound` settles it wherever it appears: nothing is there, so the path was never in the domain and the answer is whole without it. A failed DECODE settles more — `InvalidData` says what is there is not text — but an open or a lookup cannot reach that verdict, having never seen the bytes, so the two lines are drawn apart (`infra::hides_content` and `infra::hides_text`). Every surface that reads files shares them, or the same file would be outside one search's domain and a hole in another's.
    - A `--path` the caller named is an assertion about the tree, checked before the walk: one that is definitely not there is a `not_found` error, never an empty domain answered as `0`.
  - `usage`: symbols whose analysis failed, on the path whose `count` is derived from the analysed rows themselves — one that sorts or filters on reference counts has no answer to give for them and cannot emit them without inventing one. The path that settles `count` from the symbol total before any probe runs does NOT set this: a failed probe there costs that symbol its `metrics`, which the missing field already says, and dropping the row to hide it would turn a missing field into a missing row. Also set when `--max-symbols` stopped the analysis before it ran out of candidates (`analyzed` names where it stopped): unlike `--limit`, that cap ends the analysis rather than the emission, so the symbols past it never reached a filter and are absent from `count` itself.
  - `diff-impact` (its own top-level field, with the cause in `hints`): `--max-symbols` stopped the analysis before it ran out of changed symbols. Like `usage`'s cap and unlike `--limit`, it ends the analysis rather than the emission, so `changed_symbols_count`, `total_references` and `coverage` are all lower bounds over a prefix of the diff. `unmeasured_files` is the other, disjoint shortfall: files whose symbols nothing could read.
  - `map summary` and `map dir` (their own top-level field): the walk could not read part of the tree, so their counts — and `summary`'s `languages` list, which is read as "the project has no others" — are a lower bound. `map dir` scopes the question to the requested directory: a failure elsewhere in the project does not mark it, and a directory the walk could not enter reports an `io` error rather than "no indexed source files".
  - `map file` (its own top-level field): the walk could not read part of the tree, so `siblings` and `counterpart_files` are a lower bound. Both enumerate rather than rank — their emptiness reads as "this file has none" — and `counterpart_files` searches every record the walk produced, so a hole anywhere bounds it.
  - `pack` (its own top-level field): the walk could not read part of the tree, so `graph_size` — the file set the pack selected from — is a lower bound. Which files the *budget* excluded is already readable from `estimated_tokens` against `budget_tokens`; this is the exclusion nothing else would show.
  - The cap causes (`--max-symbols`, a widening cut short, an index page that filled) say the count is a lower bound without establishing that raising the cap would raise it: what lies past a cap has not been filtered, and the filters live above the source that capped. A lower bound stays true either way, and the alternative reading is worse — `truncated` alone says "3 of 6", which an agent takes for a count of 6 when the index held 60.
  - Where it does not appear at all: rankings that never claimed to enumerate and publish no count of what they ranked (`map related`, and `map file`'s `related_files` — the flag beside it speaks for that file's enumerated lists, not for its ranking).
  - What it deliberately does NOT cover: whether a source is current. An index-backed count (`backend: "index"` items) is exact for the build behind it, and that build is a snapshot — a file written since it ran has no row to find and no row to mark `stale`. That is the documented price of not re-walking the tree on every query; its signals are `backend`, `stale`, and `search index status`, and its remedy is `search index build`. Marking every index hit `incomplete` would set the flag on the common case and teach an agent to skip it. A zero is the exception, because a zero is what gets read as "nothing exists": the plain symbol and content routes confirm one against disk (an index miss rescans the tree or fans out live), and the wildcard route — which no language server can honor, so it has only the index — says so in a hint instead. A symbol zero rests on either of two confirmations, and says so when it has neither: a language server that answered the same nothing against the working tree, or an index whose build scope covered the question and whose tree has not moved since — checked by a stat-only walk, so no server is required. Failing both, a hint names the index as behind the tree and prescribes the rebuild that repairs it. So a bare symbol zero, carrying no hint and no gap, is the one answer that states an absence outright.
  - Distinct in cause from `indexing` (server still warming) and from the call-graph `incomplete` on `callees`/`impact.blast_radius` (a hop's query failed), which share the meaning "lower bound".
  - It does not restate `coverage_gaps`: a gap names a *language* the answer does not speak for, and implies a short count for that language on its own. `incomplete` says the count is short for a reason no language gap can express — every requested language was covered and the answer is still not whole. A non-empty `coverage_gaps` never by itself sets `incomplete`.
- `error` — structured `{code, message, hint}` failure, omitted on success
- `config_errors` — array of ways the on-disk config differs from what is running: a whole-config load failure (a malformed `.symora/config.toml` the run fell back from to defaults), and every key no setting consumes — a mistyped name, or one a release retired — reported as `<path>: unknown key \`<dotted.path>\`` while the rest of the file still applies. Injected as a top-level field on *any* command's output by the output layer, omitted when empty. The command proceeds on defaults; this is how an agent learns its config never applied without having to run `doctor`. A command that emits its own `config_errors` (`doctor`, `config show` — which also report the rejected-`[lsp.servers]`-stanza class) owns the key and the output layer never overwrites it.

If a new list response needs a different shape, that's a strong signal the underlying command should be reshaped instead.

## The rule a disclosure has to pass

**A disclosure states what is true now, and its remedy has to be actionable against that fact now.** Every way this has been gotten wrong so far fails one half or the other:

- Counting a shortfall only where it is discovered, while the failure also happens later (a scan's own reads, a cache's embed loop) — not true now.
- Writing a record on the failure path that makes the next run skip the retry — true on the first run only, and silent on every run after.
- Saying one failure twice because two walks over the same tree each counted it — one fact, stated as two.
- Letting a past fact stand for a present one: an index built over paths that have since been fixed prescribes `search index build --force`, which cannot read a path that is blocked *now*. Whether the rebuild is worth offering is a question about the tree, so it is asked of the tree when the disclosure is made — never inferred from what else the same command happened to walk, which is evidence only some routes can produce and made the advice flip on `--lang`.
- Letting a cap separate a remedy from its fact: hints and follow-up commands trimmed as two independent lists leave a command standing under a sentence that does not motivate it. Advice is capped as whole entries — a fact and the commands that act on it — so what survives is always a pair.

The corollary is what to do when it is unknown whether two shortfalls are the same failure: say both. A reader absorbs a fact stated twice; a reader cannot absorb a remedy that does not work.

The boundary: an unbounded list — anything whose length scales with the codebase or the finding count (references, symbols, diagnostics) — wraps in `Section<T>`, usually flattened beside the response's own fields (`refs`, `usage`, `diagnostics` all do this). Bounded summary arrays (e.g. `impact`'s `files`, capped at `IMPACT_FILES_LIMIT`) stay plain arrays.

## Field omission

Omit optional fields with `#[serde(skip_serializing_if = "Option::is_none")]`. Empty strings, zero values, or empty arrays for absent data force agents to write defensive parsing — don't make them.

## Index status coverage

A `conflict` from a search means the index is momentarily unavailable and that route reads it alone (the wildcard route) — a build owns it, or a lock is held by a daemon and a direct run at once. The remedy is the same for each: wait and retry, never build. Routes that can fall back to a language server answer instead and say so in a hint.

`unread_paths` is what any of those flags stands for: the paths a walk or a build could not read, relative to the project root, omitted when there were none. A flag without them leaves a reader with nowhere to check, and the surfaces that carry it have no rebuild to prescribe — naming the paths is the whole remedy there. `map dir` scopes its list to the directory it answers about, exactly as its flag is scoped.

`search index build` and `search index status` carry `unread_paths` only when the last completed build could not read some path — a file it could not open or a directory it could not enter, not a missing or non-text file. What those paths hold NOW is absent from an index whose scope names their language, so they qualify both the `completed` status and every later reading of `languages`; they are stored with the completion marker rather than living only in the build's own response, and every search that draws on such a build reports `incomplete` and names them in its hints. Emitted relative to the project root, as every other path in a response is.

What an EARLIER build read from them may still have rows, and those rows stay: they are durable data, and a permission change is not a deletion. That leaves them on the currency axis rather than this one — `stale`, `backend`, and `search index build` — which is why pruning is scoped to where the walk went rather than refused whenever it was turned away. Refusing it outright would keep every deleted file's rows alive across the whole project on account of one blocked directory.

Paths rather than a count, for three reasons that a count cannot serve. A remedy has to be actionable, and "3 paths" leaves a reader with `--force` and nowhere to look — `--force` cannot read a path whose permissions are the problem. A path names its own language, and the index derives a file's language from that same name, so a build turned away from `a.py` left no Rust row missing; only a path that names none (a directory, a file without an extension) puts every language back in doubt, and one of those is enough to. And a shortfall has to die with the failure it describes: a per-file refresh that reads one of these paths — or establishes the tree no longer holds it — drops that path, so the statement never outlives the hole and sends a reader to rebuild over one that is gone. What no refresh settled stays until the next build, because nothing about it changed.

`index_size_bytes` is carried by `search index status` and by nothing else. It is the store's own page count times its page size — the logical size of the index, which every connection reads identically, where the file's length would not: under WAL the pages committed since the last checkpoint live in the log, so that number would depend on when a checkpoint last ran rather than on what the index holds. It describes the store rather than any one build, which is why the build that wrote it does not report it: a size named beside a build reads as that build's cost, and what it measures keeps moving afterwards — a later build, a per-file refresh, an edit. A build returns every page it freed before it reports, so the number tracks what the index holds rather than how many times it was rebuilt, and it agrees with the file on disk. An agent reads it to decide whether an index is worth narrowing or clearing; whether a build changed anything is what the counts beside it answer.

`search index status` always carries `languages`: the languages the last completed build extracts symbols for. It is a presence-is-contract field, not a summary — row counts cannot distinguish a whole index from one a narrowed build or a per-file refresh left partial, and a symbol search's answer is complete only for the languages listed. Empty means no build has completed.

## Doctor provenance fields

`doctor` rows carry `source: "config"` and `command` only when an `[lsp.servers.<lang>]` override applies — both omitted for builtin servers, and that absence is contract: it is how an agent detects an override that failed to apply. Both fields describe what the NEXT server start will use — a warm daemon keeps its startup table until `symora daemon restart`. Top-level `config_errors` (array of strings, omitted when empty) lists config problems affecting the report: rejected `[lsp.servers]` stanzas (non-canonical keys, unknown fields, mistyped values; a stanza's unknown fields and mistyped values are reported together in one load, each message a single line) — recorded at load, never applied, never fatal to the rest of the config — and whole-config load failures (the report then reflects builtin defaults). `config show` emits the same `config_errors` array under the same name and presence rule for the rejected-stanza class, so an agent inspecting config sees the rejection where it looks first. `symbol_extraction` / `ast_search` — always-present booleans on each `languages[]` row: whether the compiled-in index extractor and the tree-sitter AST grammar cover the language (static build facts, independent of server install state).

`installed` and `serves` are always-present booleans stating two different facts, and only the second is a capability. `installed` says an executable resolves at the effective command — a version-manager shim and a working server satisfy it alike. `serves` says the server answers the LSP handshake for this workspace, verified wherever a version probe could not settle it. An agent branches on `serves`; `summary.serving` counts it. `install` is present whenever `serves` is false, and describes the repair for the state observed — installing the server, fixing the override, or diagnosing a binary that resolves but cannot run.

## Surfaces that emit JSON

- `src/cli/response/` — final user-facing output. Stability bar: API.
- `src/daemon/protocol.rs` — the JSON-RPC request/response envelope; `src/daemon/wire.rs` / `wire_error.rs` — the payload types it carries. Stability bar: API for the same reason.
- `src/mcp/tools/handlers.rs` — captures the shared command-layer JSON verbatim, so the MCP surface aligns structurally rather than by a parallel definition.

The first two must not drift from each other: if a CLI command grows a new output field, the wire type stays aligned. The MCP surface inherits the shape for free by capturing — don't reshape it there.
