# Import edges come from the parse tree

`services/imports.rs` reads a file's module references through a tree-sitter query per language, and `pack` builds its graph from those. A reference is only a reference where the grammar says one is: a Go constant holding a package path, an import written inside a comment, and a doc example are all text that scanning lines would have taken for structure, and PageRank amplifies whatever structure it is handed. Adding a language is one query plus the fixture that proves what it captures, every pattern matching a form the fixture writes — never a new line rule.

Filesystem-relative references resolve against exact project paths. An absolute reference resolves only to a file whose module name, as its language derives it, is that reference, never to a file whose path merely ends the same way; where the language's rules do not determine a target, it forms no edge. A name a build manifest declares resolves through that manifest (`Manifests` in `pack/manifests.rs`), never through a guess at which tree components are real, and a name two manifests declare names neither unless one is the importer's own. A specifier names a file of any kind it spells exactly: an edge where pack reads that file, none and nothing disclosed where it is only on disk. A name a configuration declares that names no file at all is disclosed, not dropped. Per language:

- **JVM.** A class resolves by the package its file declares and the name it declares at its top level, never by the file's own name. That name is a class or an object, which, like a Scala `val`, holds what a longer import or a wildcard reaches through it; a Kotlin or Scala function or property; or a Scala `given`, which an import names only whole. Java also names the class a Kotlin file's top-level functions and properties compile into: its `@file:JvmName`, else the file's name and `Kt`, as Kotlin forms it.
  - An importer sees its own source set and those its module builds it with: `main` and `testFixtures` from `test`, `main` from `testFixtures`, and its module's `test` or `androidTest` from an Android variant's test set.
  - An importer may see every set of its own module but a test set from code that is no test and `testFixtures` from `main`, and every set of another module that holds no tests (`main`, Kotlin Multiplatform's `commonMain`, Gradle's `testFixtures`). It never sees another module's test set: `test`, a name ending in `Test` as `commonTest` and `androidUnitTest` do, or an Android variant's, `test` or `androidTest` and the variant's name as `testDebug`. `testFixtures` is no test set.
  - Of several files declaring a class, the importer means the one in its own set, else in a set it sees, else in a set it may see; where the first of those holding any holds several, it names none. A package is the files declaring it in the sets the importer sees, else in the one other set holding it that the importer may see; where several such sets hold it, it names none.
- **Python.** A module resolves below a directory the importer's own project puts on its `sys.path`.
  - The importer's own project is the nearest directory above it that is no package, lies below no root an enclosing project puts on `sys.path` other than that project's own directory, and whose files configure a build. Below `src/` or a declared package location sit that root's packages, a namespace package needing no `__init__.py`.
  - A `setup.py` configures a build, and so does a `pyproject.toml` or `setup.cfg` other than one holding pytest's table alone; an empty one, or one that cannot be parsed, configures a build. `pytest.toml`, `pytest.ini`, their dotted names, `tox.ini` and a file holding only pytest's table configure pytest alone.
  - A project puts on its `sys.path` the directory above the importer's top-level package, a root its configuration declares, setuptools' flat or `src/` layout, and the `pythonpath` of the pytest configuration the importer runs under. That configuration is in the nearest directory configuring pytest: the first of `pytest.toml`, `.pytest.toml`, `pytest.ini`, `.pytest.ini`, `pyproject.toml` with `[tool.pytest]` or `[tool.pytest.ini_options]` but not both, `tox.ini` and `setup.cfg`, as pytest 9 reads them.
  - For a test module or `conftest.py` that pytest imports by inserting its basedir, the first directory upward without `__init__.py`, the path also holds that basedir and those of the `conftest.py` files pytest loads before it: those in its directory and the directories above it, down from the directory of the pytest configuration it runs under, else of the `pyproject.toml` pytest falls back to, else the project root. They are looked in as pytest's import mode leaves them on `sys.path`. Where it prepends, as it does by default, its own basedir comes first, then the conftests' deepest first, then every other directory; where it appends, every other directory comes first, then the conftests' outermost first, then its own.
  - The path also holds the roots of the projects in the tree its declared dependencies install, and theirs: a uv workspace member its sources mark `{ workspace = true }`, a uv or Poetry `path` dependency.
  - It never holds another project's roots otherwise, nor the directory above another top-level package, which only an installation pack does not read puts there, nor a directory merely because a script sits in it.
- **Go.** An import path resolves through the `go.mod` declaring its module, to the package below that module's root.
- **Dart.** A `package:` URI resolves through the `pubspec.yaml` declaring its package, to a file below that package's `lib`.
- **JavaScript and TypeScript.** Pack reads `import` and `export … from` declarations and TypeScript's `import x = require()`; a CommonJS `require()` call and a dynamic `import()` form no edge.
  - A non-relative specifier resolves through the `paths` and `baseUrl` of the nearest `tsconfig.json` (or `jsconfig.json`), with what it `extends`. An `extends` naming a package finds its configuration in `node_modules` as TypeScript finds it, else in the workspace package of that name. What an `extends` that cannot be read could set is left open.
  - Where that configuration has `references`, a file is compiled under the one of it and the projects they reach whose `files`, `include` and `exclude` take the file and that reach no other project taking it, as `tsc -b` builds them: a project reads a file a project it reaches compiles as that one's output. A file several such projects saying different things take is disclosed. A file none of them takes, which `tsc -b` compiles in none, is read without a configuration, and disclosed only where the nearest configuration or a project its references reach maps a specifier it writes: a `paths` pattern other than `*` matches it, or `paths` or `baseUrl` name a file for it.
  - The `package.json` name of a package a JavaScript workspace lists stands for the file its `exports` maps, through the conditions TypeScript matches for the import in their written order: `require` for an `import x = require()` and for a declaration in a file emitted as CommonJS, `import` for any other. An open condition decides nothing the keys after it do not agree on. Without `exports`, or under `node10`, which does not read it, the name stands for its `types`, `main` or `index`; under `classic`, which reads no `package.json`, for none.
  - What a configuration leaves unset, and a TypeScript file no configuration governs, is read under the defaults of the TypeScript major its workspace uses, as tsc 5.9.3, 6.0.3 and 7.0.2 apply them. That major is the `typescript` installed in the nearest `node_modules`, else the lower bound of the range the nearest `package.json` declares, pnpm catalogs and `npm:` aliases read. Where none is known, the file is read under each of 5, 6 and 7, and an edge forms only where they agree.
  - A file TypeScript does not compile, a JavaScript file no configuration takes or any file where no TypeScript is installed or declared, matches what Node and the bundlers agree on: `default`, and `import` or `require` by its form, never `types`; every other condition stays open.
  - The `paths` catch-all `*` declares no name: a specifier only it maps is a package's.
- **Rust.** A `Cargo.toml` declares its library's and its targets' names. A path resolves through its crate's module tree, built as rustc builds it from each crate root Cargo builds (the library, binaries, tests, examples, benches and build script a target names or Cargo discovers) through the `mod` declarations and `#[path]` attributes the parse tree holds. Each `use` is read from the file's module through the inline modules enclosing it.
  - `self::`, `super::`, `crate::`, a `mod` declaration and a path through a declared module name resolve to the file the tree puts there; a path that goes on into an item (an enum's variants) resolves to the file of the deepest module it passes through, which binds that item.
  - What the tree leaves open is omitted with a coverage hint: a file no crate's declarations reach, a module both `x.rs` and `x/mod.rs` could be, whose path a `cfg_attr` sets or whose declarations disagree.
  - A path from any other name is an extern crate's, which forms no edge and needs no hint.
- **Elixir, Swift.** A language that ties no module name to a file has no import query, so pack discloses it rather than reading references nothing could resolve.

A string keeps its literal quote characters and whitespace after the syntax delimiter is removed once; a string form whose semantic value is not implemented is omitted rather than its spelling being taken for a file name.
