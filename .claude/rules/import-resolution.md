# Import edges come from the parse tree

`services/imports.rs` reads a file's module references through a tree-sitter query per language, and `pack` builds its graph from those. A reference is only a reference where the grammar says one is: a Go constant holding a package path, an import written inside a comment, and a doc example are all text that scanning lines would have taken for structure, and PageRank amplifies whatever structure it is handed. Adding a language is one query plus the fixture that proves what it captures, every pattern matching a form the fixture writes — never a new line rule.

Filesystem-relative references resolve against exact project paths. An absolute reference resolves only to a file whose module name, as its language derives it, is that reference, never to a file whose path merely ends the same way; where the language's rules do not determine a target, it forms no edge. A name a build manifest declares resolves through that manifest (`Manifests` in `pack/manifests.rs`), never through a guess at which tree components are real, and a name two manifests declare names neither unless one is the importer's own. A specifier names a file of any kind it spells exactly: an edge where pack reads that file, none and nothing disclosed where it is only on disk. A name a configuration declares that names no file at all is disclosed, not dropped. Per language:

- **JVM.** A class resolves by the package its file declares and the name it declares at its top level, never by the file's own name. That name is a class or an object, which, like a Scala `val`, holds what a longer import or a wildcard reaches through it; a Kotlin or Scala function or property; or a Scala `given`, which an import names only whole. Java also names the class a Kotlin file's top-level functions and properties compile into: its `@file:JvmName`, else the file's name and `Kt`, as Kotlin forms it.
  - An importer sees its own source set and those its module builds it with: `main` and `testFixtures` from `test`, `main` from `testFixtures`, and its module's `test` or `androidTest` from an Android variant's test set (`testDebug`, `androidTestFree`), and `androidUnitTest` or `androidInstrumentedTest` from Kotlin Multiplatform's (`androidUnitTestDebug`), which are compiled together.
  - An importer may see every set of its own module but a test set from code that is no test and `testFixtures` from `main`, and every set of another module that holds no tests (`main`, Kotlin Multiplatform's `commonMain`, Gradle's `testFixtures`). It never sees another module's test set: `test`, a name ending in `Test` as `commonTest` and `androidUnitTest` do, or an Android variant's, `test`, `androidTest`, `androidUnitTest` or `androidInstrumentedTest` and the variant's name as `testDebug`. `testFixtures` is no test set.
  - Of several files declaring a class, the importer means the one in its own set, else in a set it sees, else in a set it may see; where the first of those holding any holds several, it names none. A package is the files declaring it in the sets the importer sees, else in the one other set holding it that the importer may see; where several such sets hold it, it names none.
- **Python.** A module resolves below a directory the importer's own project puts on its `sys.path`.
  - The importer's own project is the nearest directory above it that is no package, lies below no root an enclosing project puts on `sys.path` other than that project's own directory, and whose files configure a build. Below `src/` or a declared package location sit that root's packages, a namespace package needing no `__init__.py`. Such a root covers the directories below it only where a build installs its project. A project is installed where its files declare it — a `setup.py`, a `pyproject.toml` with `[project]` or `[build-system]`, a `setup.cfg` with `[metadata]` or `[options]` — except that a `pyproject.toml` uv manages is installed only with `[build-system]` unless `tool.uv.package` says otherwise, as uv documents and uv 0.13.5 installs it, so a uv workspace's virtual root, holding `[tool.uv.workspace]` alone, covers none. A `[tool.uv]` table is pack's mark of a file uv manages, not uv's own definition, which takes any `pyproject.toml` uv is run on; uv 0.13.5 writes the table wherever it relates projects: `uv add` of a workspace member or a path writes `[tool.uv.sources]`, and `uv init` in a workspace adds to its `[tool.uv.workspace]`. A directory a uv workspace lists among its `members` is never covered by that workspace's root. Below a root no build installs, or as such a member, a directory is a project only where its own files declare one, whether or not a build installs it, as uv installs the dependencies of a project it does not build; files that only configure a tool there, as ruff's `extend` does, leave it the enclosing project's.
  - A `setup.py` configures a build, and so does a `pyproject.toml` or `setup.cfg` other than one holding pytest's table alone; an empty one, or one that cannot be parsed, configures a build. `pytest.toml`, `pytest.ini`, their dotted names, `tox.ini` and a file holding only pytest's table configure pytest alone.
  - A project puts on its `sys.path` the directory above the importer's top-level package, a root its configuration declares, setuptools' flat or `src/` layout, and the `pythonpath` of the pytest configuration the importer runs under. That configuration is in the nearest directory configuring pytest: the first of `pytest.toml`, `.pytest.toml`, `pytest.ini`, `.pytest.ini`, `pyproject.toml` with `[tool.pytest]` or `[tool.pytest.ini_options]` but not both, `tox.ini` and `setup.cfg`, as pytest 9 reads them.
  - For a test module or `conftest.py` that pytest imports by inserting its basedir, the first directory upward without `__init__.py`, the path also holds that basedir and those of the `conftest.py` files pytest loads before it: those in its directory and the directories above it, down from the directory of the pytest configuration it runs under, else of the `pyproject.toml` pytest falls back to, else of the nearest `setup.py`, else the project root. They are looked in as pytest's import mode leaves them on `sys.path`. Where it prepends, as it does by default, its own basedir comes first, then the conftests' deepest first, then every other directory; where it appends, every other directory comes first, then the conftests' outermost first, then its own.
  - The path also holds the roots of the projects in the tree its declared dependencies install, and theirs: a uv workspace member its sources mark `{ workspace = true }`, a uv or Poetry `path` dependency.
  - It never holds another project's roots otherwise, nor the directory above another top-level package, which only an installation pack does not read puts there, nor a directory merely because a script sits in it.
- **Go.** An import path resolves through the `go.mod` declaring its module, to the package below that module's root.
- **Dart.** A `package:` URI resolves through the `pubspec.yaml` declaring its package, to a file below that package's `lib`.
- **JavaScript and TypeScript.** Pack reads `import` and `export … from` declarations and TypeScript's `import x = require()`; a CommonJS `require()` call and a dynamic `import()` form no edge.
  - A non-relative specifier resolves through the `paths` and `baseUrl` of the nearest `tsconfig.json` (or `jsconfig.json`), with what it `extends`. TypeScript 7 reads no `baseUrl`: nothing resolves below it, and `paths` resolve against the directory of the configuration declaring them. A `jsconfig.json`'s `baseUrl` is read whatever the major, since the bundler building its JavaScript project reads it: Next.js 16.3.3 and esbuild 0.28.2 do with TypeScript 7.0.2 installed. An `extends` naming a package finds its configuration in `node_modules` as TypeScript finds it, else in the workspace package of that name. An `extends` that cannot be read leaves `module`, `moduleResolution`, `target` and `customConditions` open; `paths`, `baseUrl`, `files`, `include` and `exclude` are read from the configurations the chain does read.
  - Where that configuration has `references`, a file is compiled under the one of it and the projects they reach whose `files`, `include` and `exclude` take the file and that reach no other project taking it, as `tsc -b` builds them: a project reads a file a project it reaches compiles as that one's output. A file several such projects saying different things take is disclosed; it is read under each of their module options, and matches a custom condition all of their configurations list, none that none lists, and leaves one only some list open. A file none of them takes, which `tsc -b` compiles in none, is read without a configuration, and disclosed only where the nearest configuration or a project its references reach maps a specifier it writes: a `paths` pattern other than `*` matches it, or `paths` or `baseUrl` name a file for it.
  - The `package.json` name of a package a JavaScript workspace lists stands for the file its `exports` maps — a subpath through its exact key, else the pattern key whose part before `*` is longest, the longer key on a tie, the same lookup `extends` uses — through the conditions TypeScript matches for the import in their written order: `require` for an `import x = require()` and for a declaration in a file emitted as CommonJS, `import` for any other. An open condition decides nothing the keys after it do not agree on. Without `exports`, or under `node10`, which does not read it, the name stands for its `types`, `main` or `index`; under `classic`, which reads no `package.json`, for none. There, past `paths` and `baseUrl`, a non-relative specifier names the first file the importer's directory or one above it holds by its name with `.ts`, `.tsx` or `.d.ts`, a written `.js` stripped and then kept, else with `.js` or `.jsx`, as tsc 5.9.3 and 6.0.3 look it up; a directory's `index`, `.mts` and `.cts` they never try. The walk is read up to the project's root. A JavaScript file it finds is disclosed where a `node_modules/@types` above the importer holds a package by the specifier's name, which tsc looks in first, and a specifier writing another script extension is disclosed.
  - What a configuration leaves unset, and a TypeScript file no configuration governs where TypeScript is installed or declared, is read under the defaults of the TypeScript major its workspace uses, as tsc 5.9.3, 6.0.3 and 7.0.2 apply them. That major is the `typescript` installed in the nearest `node_modules`, else the major pack reads from the range the nearest `package.json` declares, pnpm catalogs and `npm:` aliases read: that of a caret, tilde or exact version or an x-range (`^5.9.0`, `~6.0`, `6.x`), or of a set of comparators bounded within one major (`>=5.0.0 <6.0.0`), every `||` alternative agreeing. A `>` bound is read as admitting its own major and a hyphen range is not read, so `>5 <7` and `5.0.0 - 5.9.9`, which npm reads as 6.x and 5.x, give none. A major below 5 is read as 5, which keeps the `module` and `moduleResolution` defaults TypeScript documents for every earlier major. Where none is known — none installed or declared, a range pack reads no major from, a major above 7 — the file is read under each of 5, 6 and 7, and an edge forms only where they agree. There an option tsc 7.0.2 rejects as an error, `ignoreDeprecations` set or not, rules 7 out where none is installed or declared, where the version installed is above 7 or no number, and where a declared range has an `||` alternative that admits a major below 7 as pack reads its comparators, or that pack reads no bound from (`latest`, `*`), as no project builds under 7 with one; a configuration setting it is read there under 5 and 6 alone. A declared range admitting only 7 and above (`>=7`, `7.x || 8.x`, `^8.0.0`) keeps 7, and what the majors read apart there is disclosed, as no major it admits builds such a project. Pack applies this to `baseUrl` (TS5102), `moduleResolution` `node`, `node10` or `classic` and `module` `amd`, `umd` or `system` (TS5108), and `module` `none` (TS6046); tsc 7.0.2 rejects an ES3 or ES5 `target` and `outFile` too, which pack reads alike under 6 and 7. An import one configuration, or the defaults, reads apart under those majors is disclosed as one the TypeScript version decides, naming a declared range pack reads none of them from, which installing `typescript`, or declaring it as a caret, tilde, exact or x-range version of 5, 6 or 7, settles. In a `jsconfig.json`'s JavaScript project, and in a file several projects saying different things take, such an import is disclosed as one the configuration does not determine.
  - A file no configuration governs that TypeScript does not compile — a JavaScript file, or any file where no TypeScript is installed or declared — matches what Node and the bundlers agree on: `default`, and `import` or `require` by its form, never `types`; every other condition stays open. A file a configuration governs is read under it whether or not TypeScript is installed. Node and the bundlers take a package without `exports` for its `main`, else its `index`, never its `types`; a `module` or `browser` field naming another file leaves the name open, not a subpath, which names the file it spells below the package. They stop at the first `exports` key that matches, and at an array's first entry, so one whose target names no file is disclosed, where TypeScript passes over it to the next key or entry.
  - The `paths` catch-all `*` declares no name: a specifier only it maps is a package's.
- **Rust.** A `Cargo.toml` declares its library's and its targets' names. A path resolves through its crate's module tree, built as rustc builds it from each crate root Cargo builds (the library, binaries, tests, examples, benches and build script a target names or Cargo discovers) through the `mod` declarations and `#[path]` attributes the parse tree holds. Each `use` is read from the file's module through the inline modules enclosing it.
  - `self::`, `super::`, `crate::`, a `mod` declaration and a path through a declared module name resolve to the file the tree puts there; a path that goes on into an item (an enum's variants) resolves to the file of the deepest module it passes through, which binds that item.
  - What the tree leaves open is omitted with a coverage hint: a file no crate's declarations reach, a module both `x.rs` and `x/mod.rs` could be, whose path a `cfg_attr` sets or whose declarations disagree.
  - A path from any other name is an extern crate's, which forms no edge and needs no hint.
- **Elixir, Swift.** A language that ties no module name to a file has no import query, so pack discloses it rather than reading references nothing could resolve.

A string keeps its literal quote characters and whitespace after the syntax delimiter is removed once; a string form whose semantic value is not implemented is omitted rather than its spelling being taken for a file name.
