# src/services — Backend Service Rules

These services back the CLI and MCP surfaces. They abstract over LSP transports, the SQLite index, and the structural search engine.

## Store durability

The SQLite index at `.symora/store.db` is product reliability, not a cache. Rules:

- `INIT_SCHEMA` is the authoritative shape, run on every open. Each of its statements leaves what it finds in place, so opening a store that holds the shape writes nothing and waits on no other process's write — a build's publication holds one open for longer than a command is given. What SQLite writes every time it runs (`NEW_FILE_PRAGMAS`, and `SCHEMA_STAMP`, written once the shape is complete) goes only to a file not yet stamped. Bump `SCHEMA_VERSION` (and the `user_version` in `SCHEMA_STAMP`) whenever the on-disk shape changes.
- Schema mismatch triggers `recover_db` (rename to `.bak`, recreate). No hand-rolled `ALTER TABLE` migrations — they hide real failures behind expected duplicate-column errors.
- Never clear the index during normal daemon idle or shutdown. The index is what makes warm starts fast.

Row mutation takes a turn rather than merging: `.symora/index.lock` (via `infra::file_lock`) is held exclusively by a build until it publishes — and, where its caller stopped awaiting it, until the work it left on the connection has run (`BuildWindow`), so no process reads a build still writing as an index nobody builds; the upkeep after it changes no row, and a lock held through it reads as a rebuild to the searches waiting on the build, which is why the checkpoint SQLite would run inside the publication's commit is left to that upkeep — and by `clear`, shared by a per-file refresh, and waited on when the database file itself is replaced. The lock keeps the destructive windows from overlapping; the build epoch in `meta` keeps the completion marker honest when a lock did not hold — deleted, not carried by the filesystem — by guaranteeing the marker was written by whoever last owned the index. It does not fence row writes; that is the lock's job, and without one an overtaken build's rows outlive it until the next build prunes them. Neither replaces the other.

Whether the index may be answered from is the durable completion marker, read in the same transaction as the rows it qualifies — never a flag a handle caches, or the daemon and a direct run would disagree about a build the other made. Every operation that destroys rows opens a build window first (marker off, epoch advanced) and may publish completion only while it still owns that epoch, so an interrupted, cleared, or overtaken build leaves a store that reads as never built — slower, never wrong. The extractor that produced the rows is recorded in the transaction that empties the store, so a first build cut off partway leaves rows the next build keeps as current instead of starting over. A search answers for the requested languages the marker covers and says which those are, so whatever the caller reads live is disjoint from what the index served. That marker is also what lets a build without one behind it drop the text-index triggers and build the whole FTS index in one pass at the end (an order of magnitude cheaper than a row at a time): nothing consults an index that has not published, opening the store leaves incomplete builds untouched, and the next build takes the same path and rebuilds. Removing the completion marker and disabling triggers is one transaction; FTS rebuild, trigger restoration, and completion publication is another. Clearing an index disables triggers before removing content rows and resets FTS in the same transaction, including after an interrupted build. A build that *does* inherit a published index keeps them, because one pass over the whole table would cost more than the rows it changes.

The build scope recorded at index time is load-bearing, not bookkeeping: `content_languages` (the languages whose files the build indexed) and `indexed_languages` (those of them with a symbol extractor) derive from it, and search routes on those sets — a name in a covered language that the index matches is answered from the index alone; an uncovered language, or a name the index does not match, pays for a live workspace query or a scan of the tree. A path query (`/`, `[`) asks live servers whatever the coverage, and the index supplements its answer; `--workspace-symbols` asks live servers only. The unrestricted scope is every code language (`Language::is_code`), and a language's coverage is every extension it declares, never a hand-kept extension list that can drift from `Language::extensions`. Widening what a build claims to cover silently widens what search treats as authoritative.

## Test-versus-production classification

`services/test_scope.rs` answers two different questions and they must not be conflated. `is_test_file` is a path question, for ranking and whole-file summaries. `TestClassifier::is_test_code` is a position question, for anything that counts a reference as coverage rather than as a production dependency.

The position answer adds regions the LANGUAGE excludes from a production build (`infra/ast/test_regions.rs` — Rust's `#[cfg(test)]` and `#[test]`). That bound is deliberate: syntax-based classification has a narrower scope than framework naming conventions; it does not establish executed coverage. Paths are classified relative to the project root so a checkout under an ancestor named `tests` does not classify production files as tests. Adding a language means finding its conditional-compilation rule, not its test-framework vocabulary.

## Declarations come from the parse tree

`services/symbols.rs` reads a file's declarations through one query per language, and the index, the AST fallback, signatures and diff-impact all read what it reads, so a form it misses answers as absent wherever the index answers alone. The same rules hold in every language:

- A variable is a declaration where it names a module's or a member's value, never where a function's scope holds it; a local function or type is still read. Anchor the query where the language declares members rather than filtering its captures afterwards; a construct both a module and a function body can hold (Python's `if`, a C preprocessor conditional) is anchored, then judged by its nearest scope (`declares`).
- A name is what the grammar binds: an assignment declares only the names its targets bind, a destructuring pattern each name it binds, a C/C++ declarator its innermost name. The scan of a node's identifier children serves nodes named that way, never one whose own rule found no name.
- A symbol's container is the nearest enclosing declaration the query captures, a namespace passed through. A declaration's parameters and type are its header and contain nothing, except a type's own, which hold its members, and a record type it defines without a name of its own (`typedef struct { … } T`, Go's `inner struct{ … }`), which takes its name.
- A parameter declares a member only where its language says so: a modifier, `val`/`var`, a case class's first list, a promoted parameter, a record component.
- C and C++ are read again past a macro the grammar cannot expand, spelled as blanks so every offset holds, only where the grammar's structure proves it one (a `::` after a declarator's name, a prototype's parameters in a second pair of parentheses, a class key before a block read as a function), never by its spelling (capitals, an `_API` suffix); a preprocessor conditional after such a class's name is read the same way, through its first branch. The grammar's recovery is not local: a proved blank can still change the reading elsewhere, and what a file reads depends on the blanks taken together. Neither the bytes the re-read tree holds in errors nor the declarations it keeps tells a better reading from a worse one, so each blank needs a proof of its own rather than a check on the result.

`DECLARATION_FIXTURES` is the contract per language: a form or a language joins it with the query that reads it, and every pattern of a query matches a form its fixtures write. Where a language server is installed, its document symbols are the reference to compare a change against.

No two declarations of a file share a name position: the index keeps one row per position and the language-server join matches by it, so a declaration that writes no name of its own (an unnamed Dart primary constructor) is placed at syntax it does write.

`declaration_visibility` answers `is_exported`; its contract is in `.claude/rules/json-output-stability.md` (Symbols and analysis).

## Import references come from the parse tree

`services/imports.rs` reads a file's module references through a tree-sitter query per language: a reference is only one where the grammar says so, never a line that spells a path. `map file` matches them, and the names a Python `from` import takes (`python_module_names`), against the names a file answers to, to list the tests importing it; how it attributes them is in `cli/commands/map/tests_of.rs`.

## Service abstractions: LSP and Store

`LspService` and `StoreService` are the traits every command speaks to. Each has two interchangeable implementations, chosen once above the mode boundary:

- `Default*` — in-process (direct LSP child processes; the store's SQLite opens lazily on first use).
- `Daemon*` — forwards to a `symora daemon` over a Unix socket.

Both implementations preserve the same result semantics and error contracts. Compare payloads under equivalent source and server state; indexing can change observations between calls (invariant #3). A read against a missing store reports `NotInitialized` and creates nothing — no `.symora/`, no empty store; only a build or an edit does — so the caller answers from its live source instead — a filesystem scan for content — or, for symbols, builds the index first where the root is in a git work tree and the search may write — never on a read-only MCP server — and answers from language servers where it may not or where that build fails; a present-but-unopenable store surfaces the real error. A search's build, and its wait for one already running, spend the search's `lsp.timeout_secs` budget: in process the budget cuts its build off, and the next build resumes it; a daemon is sent what remains, runs the build on its own task holding the project in use, and answers by then that the build still owns the index. Either way the budget is spent and no server is asked. A `search index build` has no budget in either mode and waits out a build in progress before running. The budget cannot cut a SQLite transaction short, so two things keep a build's last transaction, the publication, from holding a search past it. A store handle reads through a read-only connection of its own and writes through another, one write at a time: under WAL the reader answers from the last committed state while a build's transaction runs, so no read — a status or a search, in the daemon whose build it is or in any other process — queues behind the build's work, and each finds the build from the marker it took away and the lock it holds. And a one-shot process exiting after its search's budget cut a build off abandons the build's work (`Store::abandon_unfinished_build`): what is queued is dropped, the running transaction is interrupted and rolls back, and the process exits at once. The cost is that a one-shot CLI whose publication alone outlasts the budget never finishes the index through searches; the remedy each such answer gives, `search index build`, has no budget and always does. A process that serves (`mcp serve` in process, the daemon) never abandons, so the work completes there and its later searches find it.

Rename captures its request-document hash before the retry loop and retains it across all attempts and server restarts.

## Symbol cache invalidation

`SymbolCache` holds one entry per path, valid only while the file's content hash matches the one it was computed from, so editing a file invalidates its entry — don't add path-only invalidation paths that break this. Entries also expire after a TTL, and eviction is oldest-first by insertion time (`created_at`, not touched on read) at the `max_entries` cap; size limits are enforced, not advisory.

## Fallback strategy

Position resolution follows the anchor contract in `src/cli/CLAUDE.md`; it must not select a nearby unrelated declaration.
